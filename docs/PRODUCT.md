# 《主播模拟器》产品定义

> 文档状态：Phase 0 基线  
> 更新日期：2026-09-14

## 1. 产品概述

《主播模拟器》是一款中文、移动端优先、竖屏运行的 H5 独立小游戏。玩家扮演一个在小房间里从零开始做网络主播的普通年轻人，通过文字选择、数值养成和随机事件，走完一段约 30 天的主播生涯，并抵达提前退场或正常生涯结局。

游戏关注的不只是“做大数值”，而是选择留下的长期后果：一次直播间对线可能带来短期流量，也可能积累黑粉、形成争议标签，并在数天后影响平台推荐、品牌合作甚至法律风险。玩家应能感受到自己的主播人生是被一连串选择塑造出来的。

一句话体验：

> 一个普通人在自己的小房间里，疲惫地追逐成为百万主播的梦想。

## 2. 产品定位

- 平台：移动端 H5 优先，兼容常见桌面浏览器。
- 屏幕方向：竖屏。
- 语言：首发中文。
- 类型：文字选择 + 数值养成 + 随机事件 + 多结局。
- 单局结构：正式版本约 30 天，每天 3 个事件；开发期先制作小型 Vertical Slice。
- 单机能力：第一阶段无后端、登录、支付、平台 SDK 和 AI API；存档使用 `localStorage`。
- 内容基调：年轻、有互联网感、有梗，带少量荒诞、黑色幽默和疲惫感，但最终温暖且保留希望。

## 3. 核心体验支柱

### 3.1 选择有后果

事件不是彼此孤立的随机题目。选择会改变属性、隐藏属性、Tag 和历史记录，进而改变后续事件的可用性、出现概率、选项以及最终结局。

### 3.2 角色真正不同

初始角色不只提供数值加减。角色还会影响：

- 事件池与事件权重；
- 角色专属选项；
- 剧情分支；
- 天赋与成长路线；
- 某些结局的达成方式。

### 3.3 随机但可解释

随机事件带来重玩价值，但结果必须受玩家状态和历史选择影响。人生报告应帮助玩家理解关键因果，而不是让成功或失败显得完全由运气决定。

### 3.4 短局内形成个人故事

数值是叙事的支撑。每局结束时，玩家应该能复述几件属于这一局的事情，例如“靠对线爆红，后来却丢了品牌合作”。

## 4. 核心循环

1. 选择初始角色。
2. 应用角色的初始属性、隐藏属性、Tag、天赋和事件修正。
3. 开始主播生涯。
4. 每天经历 3 个事件。
5. 每个事件选择 1 个可用选项。
6. 结算显性属性、隐藏属性、Tag、剧情状态和历史记录。
7. 每次选择后检查立即结果和特殊 Game Over。
8. 若未结束，进入下一事件或下一天。
9. 活到最终日后，根据完整状态匹配正常结局。
10. 生成《主播人生报告》。

正式版本的目标天数是 30 天。Vertical Slice 的天数和内容规模由对应阶段单独确定，不以填满 30 天为目标。

## 5. 初始角色

### 5.1 颜值新人

- 优势：镜头感强、初始人气较高、涨粉更容易。
- 代价：舆论风险更高、抗压能力较弱。
- 潜在路线：颜值流量、品牌合作、舆论风波。

### 5.2 搞笑社牛

- 优势：互动能力强、容易制造节目效果、更容易触发爆款。
- 代价：更容易招黑和制造争议。
- 潜在路线：整活爆红、连麦社交、黑红主播。

### 5.3 才艺选手

- 优势：内容稳定、口碑较高、核心粉丝忠诚度容易增长。
- 代价：前期涨粉相对较慢。
- 潜在路线：长期主义、小而美、专业内容主播。

### 5.4 富二代体验生活

- 优势：初始财富高，能承担更多高成本选项。
- 代价：初始路人缘一般，容易受到身份质疑。
- 潜在路线：高投入直播、资源型成长、口碑逆转或炫富争议。

角色的具体初始数值与概率修正属于平衡配置，不在本产品基线中锁死。

## 6. 状态系统

### 6.1 玩家可见属性

| 字段 | 中文名 | 含义 |
| --- | --- | --- |
| `popularity` | 人气 | 当前热度和被看见的程度 |
| `fans` | 粉丝 | 累积关注者规模 |
| `reputation` | 口碑 | 大众对主播的总体评价 |
| `money` | 财富 | 可支配资源与累计收入 |
| `mentality` | 精神状态 | 持续直播和承受压力的能力 |
| `violation` | 违规值 | 平台违规风险；越高越危险 |

### 6.2 隐藏属性

| 字段 | 中文名 | 主要影响 |
| --- | --- | --- |
| `haters` | 黑粉值 | 带节奏、争议传播与舆情事件 |
| `platformTrust` | 平台信任 | 推荐、限流、封禁等平台反馈 |
| `loyalty` | 核心粉丝忠诚度 | 粉丝留存、应援与危机支持 |
| `commercialValue` | 商业价值 | 品牌商务、报价与商业路线 |
| `legalRisk` | 法律风险 | 合同、隐私、广告与诉讼事件 |

隐藏属性不直接展示精确值。UI 可以通过文案、气氛或事件反馈提供模糊线索，避免玩家完全盲猜。

### 6.3 Tag

Tag 表示离散且可持续的身份、经历或状态，是事件条件和结局条件的重要组成部分。首批概念包括：

- `controversial`：争议主播；
- `viral`：出现过爆款；
- `signedMCN`：已经签约 MCN；
- `hasBigSpender`：出现核心大哥；
- `burnout`：过度疲劳；
- `goodReputation`：口碑主播。

Tag 需要稳定的机器 ID 和独立中文展示文案。短暂状态如果只持续若干事件或若干天，应使用带期限的状态机制，避免把所有状态都堆成永久 Tag。

## 7. 事件系统

事件是游戏的核心内容单元。一个事件至少描述：

- 稳定唯一的 Event ID；
- 标题、剧情描述和事件类型；
- 可选的具体时间、地点与场景化叙事；
- 可出现的天数或阶段；
- 基础权重与动态权重修正；
- 前置事件和历史选择；
- 必需 Tag、禁止 Tag；
- 属性与隐藏属性条件；
- 角色限制；
- 2～3 个选项；
- 无候选事件时的安全兜底策略。

一个选项可以产生：

- 显性属性变化；
- 隐藏属性变化；
- 添加或移除 Tag；
- 解锁或屏蔽事件；
- 记录关键选择；
- 设置阶段性剧情标记；
- 立即触发特殊结果；
- 一段结算反馈文案。

事件选择流程应为：筛选满足条件的候选事件 → 应用角色、Tag 和状态带来的权重修正 → 按权重抽取 → 防止不合适的近期重复 → 展示事件。

### 7.1 因果链示例

“黑粉在直播间带节奏”中选择“直接和他对线”：

1. 当下获得 `popularity +8`、`haters +15` 和 `controversial`。
2. 后续因为 `controversial`，提高“对线切片爆火”的出现概率。
3. 爆火后获得 `viral`，同时进一步改变舆论和商务事件池。
4. 当 `controversial`、相关历史事件与商业合作同时存在时，可能触发“品牌取消合作”。

这类短期收益与长期代价的组合，是内容设计的主要模板。

## 8. 结局系统

### 8.1 提前结束（Game Over）

- 永久封禁：与违规值、平台信任、违规历史和相关 Tag 共同相关。
- 缠上官司：与法律风险以及特定合同、商业或隐私事件相关。
- 我不播了：与精神状态、`burnout` 和长期压力历史相关。

Game Over 不应全部由单一阈值触发。结局条件可以组合属性、Tag、历史事件、关键选择和连续状态，并给出可理解的叙事原因。

### 8.2 正常结局

玩家存活到最终日后，按优先级从符合条件的结局中选出最终结果。候选方向包括：

- 全网顶流；
- 黑红顶流；
- 小而美主播；
- 带货机器；
- 争议主播；
- 佛系主播；
- 平平无奇的小主播。

必须设置一个无条件兜底结局，保证任何合法状态都能完成结算。

## 9. 主播人生报告

最终报告至少包含：

- 最终结局；
- 主播人格；
- 生存天数；
- 最终粉丝、财富和口碑；
- 重要选择；
- 重大事件；
- 主播人生总结。

报告优先回答“我成为了谁”，而不是默认铺开整份操作日志。完整人生轨迹由玩家主动展开，并展示事件时间、地点、选择、显性属性影响和隐藏反馈。

第一阶段使用规则与文案模板生成报告。未来可以接入生成式 AI，根据本局历史生成个性化总结，但 AI 不能成为结局判定或存档可用性的前置依赖。

## 10. 视觉与交互方向

核心场景是夜晚的小卧室或小直播间：电脑、手机、麦克风、耳机、环形灯、RGB 灯、饮料、快递箱、玩偶、贴纸、城市夜景，以及 `LIVE`、`ON AIR`、弹幕、礼物和粉丝通知等直播元素。

- 风格：真实感的中等粗粒度像素画、中国独立像素游戏。
- 色彩：深靛蓝 / 紫色为主，品牌粉为强调色。
- 界面：像素独立游戏 HUD 与直播浮层融合。
- 情绪：温暖、略疲惫、带互联网黑色幽默，“很累，但还在做梦”。
- 实现：主要 UI 优先使用 HTML / CSS；图片用于角色、场景、事件和结局插图。

明确排除：赛博朋克、日韩二次元手游、SaaS Dashboard、3D、写实，以及高清插画简单套像素滤镜。

## 11. 第一阶段不做的内容

- 30 天完整内容量；
- 后端、账号与跨设备存档；
- 数据库；
- 支付；
- TapTap SDK；
- AI API；
- 大规模具体事件创作；
- 完整商业化设计。

## 12. 产品验收原则

每次迭代优先回答一个明确问题。任何新增功能应至少满足以下原则：

- 内容配置不直接散落在 React 组件中；
- 玩家选择能被历史记录，并可影响后续内容；
- 游戏状态可保存、恢复并解释；
- 移动端竖屏下可读、可点、反馈明确；
- 无论随机结果如何，都存在合法的继续或结束路径。

## 13. 需要提前关注的风险

1. **事件组合爆炸与死路**：条件、前置和互斥关系增多后，容易出现抽不到事件、剧情断链或内容永远无法触发。需要可验证的条件模型、兜底事件和内容图检查工具。
2. **随机性破坏因果感**：纯权重抽取可能让前期选择没有明显回响。关键因果链应通过解锁、保底、冷却和权重修正共同保障，并在报告中回溯原因。
3. **数值、Tag 与临时状态失控**：把所有规则都做成任意脚本或永久 Tag，会很快难以平衡和迁移。需要受控的声明式条件 / 效果模型，以及明确区分永久经历与限时状态。
4. **存档随内容升级失效**：事件 ID、字段和规则会持续变化。首版就应包含 schema 版本、稳定 ID、迁移入口和损坏存档回退策略。
5. **移动端文字体验过载**：属性、直播浮层、长剧情和 2～3 个选项同时出现，容易拥挤。Vertical Slice 必须尽早在窄屏真机尺寸验证信息层级、点击区域和单次阅读量。
