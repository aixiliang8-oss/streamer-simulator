# 《主播模拟器》开发路线

> 路线原则：一次只解决一个明确问题；每个阶段达到验收标准后再扩大范围。  
> 更新日期：2026-09-14

## 当前进度

- Phase 0：已完成产品与技术基线文档。
- Phase 1：已完成 React + TypeScript + Vite 工程与质量基线。
- Phase 2：已完成首个可玩的 Vertical Slice。
- Phase 2.5：已完成因果提示、隐藏属性定性反馈、违规风险反馈与“黑红边缘人”结局。
- Phase 2.6：已将固定剧情扩展为四阶段、二十个主播成长事件。
- Phase 3：已完成 Narrative Upgrade，让选择体现价值观取舍，并把结局升级为“命运结果 + 主播人格画像”。
- 下一阶段：等待下一步指令，不自动进入随机 Event Engine、角色扩展或存档开发。

## Phase 0：理解项目 + 建立项目规范

目标：把共同认知固化为后续开发可读取的文档。

交付物：

- 产品定位、核心循环、角色、属性、事件与结局定义；
- 推荐工程分层和核心数据实体关系；
- Phase 0～10 路线图；
- 前置风险和阶段边界。

验收标准：

- `docs/PRODUCT.md`、`docs/TECHNICAL_PLAN.md`、`docs/ROADMAP.md` 可作为后续任务入口；
- 本阶段不创建游戏功能和大量剧情；
- `sources/` 中同步资料保持只读。

## Phase 1：初始化工程

状态：已完成（2026-09-14）。

目标：建立能运行、能检查、能测试的 React + TypeScript + Vite 空壳。

建议范围：

- 初始化 React + TypeScript + Vite；
- 配置 TypeScript 严格模式；
- 配置 lint、格式化和基础测试；
- 建立建议目录与最小移动端页面骨架；
- 设置全局 CSS reset、基础设计令牌和 viewport；
- 添加最小 README，记录开发、测试和构建命令。

不做：正式事件引擎、完整角色数据、存档和大量视觉设计。

验收标准：

- 开发环境可启动；
- 类型检查、测试和生产构建通过；
- 手机尺寸下能显示无横向溢出的项目占位页；
- 目录边界与技术方案一致。

## Phase 2：非常小的 Vertical Slice

状态：已完成（2026-09-14）。

目标：用最少内容验证“选择角色 → 经历事件 → 看到后果 → 获得结局”的完整体验是否成立。

建议范围：

- 先接入 1 个角色；
- 1～2 个游戏日，每天 3 个事件；
- 少量固定或半随机事件，其中至少 1 条跨事件因果链；
- 显性属性 HUD；
- 1 个提前结束结局和 2 个正常结局；
- 简版人生报告；
- 暂时允许引擎能力只覆盖切片所需规则。

验收标准：

- 一局可从开始走到结束；
- 至少一个早期选择会改变后续事件或选项；
- 刷新不作为主要验收项，内容量不向 30 天扩张；
- 在真实窄屏尺寸完成一次体验检查。

## Phase 3：Narrative Upgrade

状态：已完成（2026-09-14）。

目标：让固定剧情中的选择形成可辨认的成长路径，并让终局回答“玩家最终成为了什么样的主播”。

本阶段范围：

- 平衡现有选项的短期收益与长期代价；
- 为现有事件补齐时间、地点与具体场景；
- 用选择文案表达陪伴、流量、商业、边界与自我节奏等价值观；
- 增加深夜陪伴、流量爆发、商业化、黑红边缘、慢热坚持、离开直播与永久封禁等命运结果；
- 在报告中输出结构化主播人格，包括标题、标签与描述；
- 报告默认聚焦命运和成长画像，完整人生轨迹按需展开；
- 保持固定事件顺序、`GameState` 与既有引擎推进机制不变。

验收标准：

- 主要选项同时存在可理解的收益和代价；
- 不同属性、隐藏属性和 Tag 组合能匹配不同主播命运；
- 人生报告展示与结局一致的人格画像；
- 游戏规则仍完全独立于 React。

## 后续：建立正式 Event Engine

目标：把切片中的临时规则整理为可扩展、可验证、可复现的正式引擎。

建议范围：

- 统一条件与效果模型；
- 带种子的权重抽取；
- 重复、冷却、解锁、屏蔽和兜底策略；
- Tag、隐藏属性、历史选择和限时状态；
- 每次选择后的 Game Over 检查；
- 内容注册与自动校验；
- 引擎和因果链测试。

验收标准：

- 引擎完全独立于 React；
- 相同 seed 和选择序列得到相同结果；
- 无候选事件时不会卡死；
- 非法内容配置能在开发 / 测试阶段被发现。

## Phase 4：完整角色系统

目标：让四名初始角色拥有可感知的玩法差异。

建议范围：

- 接入颜值新人、搞笑社牛、才艺选手、富二代体验生活；
- 角色初始状态与天赋；
- 角色事件权重修正；
- 角色专属选项或剧情；
- 角色选择界面和差异说明；
- 角色平衡基线测试。

验收标准：

- 每个角色至少有一种非数值差异；
- 同一事件可因角色而出现不同概率或选项；
- 角色定义不侵入 UI 和通用引擎。

## Phase 5：扩充剧情内容

目标：逐步形成能支撑目标局长的主播生态与因果网络。

建议范围：

- 按主题建立事件链：冷场、黑粉、榜一、礼物、连麦、MCN、商务、爆款、舆论、平台、粉丝关系、主播关系和法律风险；
- 建立内容表、事件 ID 规范和写作模板；
- 分批扩充，而不是一次填满 30 天；
- 建立事件可达性、频率和重复度报告；
- 持续试玩和平衡。

验收标准：

- 关键主题至少形成短期反馈与延迟后果；
- 多局体验存在明显差异，且不会频繁重复相同事件；
- 主要事件链没有已知死路或不可达节点。

## Phase 6：接入视觉资源并重构 UI

目标：把验证过的玩法转化为统一、有辨识度的正式视觉体验。

建议范围：

- 整理用户提供的视觉参考和资产规范；
- 接入角色、场景、事件和结局插图；
- 完成卧室直播间主场景；
- 重构 HUD、直播浮层、弹幕、礼物和通知；
- 建立素材尺寸、压缩、加载与降级策略；
- 适度加入符合氛围的动效和音效入口。

验收标准：

- 视觉符合既定像素艺术方向和情绪；
- 不呈现赛博朋克、二次元手游或 SaaS Dashboard 观感；
- 首屏加载与低性能移动设备体验可接受；
- 长文案、刘海屏和安全区域表现正常。

## Phase 7：完善 Ending / Game Over

目标：让提前退场和正常结局具备组合条件、清晰因果和足够区分度。

建议范围：

- 永久封禁、缠上官司、我不播了；
- 全网顶流、黑红顶流、小而美主播、带货机器、争议主播、佛系主播及兜底结局；
- 结局优先级和冲突规则；
- 结局解锁提示、插图入口和原因说明；
- 结局覆盖率自动测试。

验收标准：

- 任意合法终局状态都有且只有一个最终结局；
- 重要结局不依赖单一数值阈值；
- 玩家能从结局反馈理解关键成因。

## Phase 8：主播人生报告

目标：把本局经历整理成值得阅读、分享和复盘的个人故事。

建议范围：

- 主播人格规则；
- 生存时间与最终数据；
- 重要选择和重大事件筛选；
- 基于模板的主播人生总结；
- 移动端报告页与分享图预留。

验收标准：

- 报告内容只来自本局真实状态和历史；
- 能体现至少 2～3 个重要因果；
- 无 AI 服务也能稳定生成完整报告。

## Phase 9：AI 个性化总结

目标：在规则报告稳定后，用生成式 AI 增强个性化叙事。

前置条件：

- 产品确认需要 AI 且明确成本、隐私与降级策略；
- 引入安全的服务端代理，不在前端暴露密钥；
- 定义输入裁剪、输出审核、超时和失败回退。

验收标准：

- AI 结果不改变结局判定；
- 服务不可用时回退到 Phase 8 的模板报告；
- 不向模型发送无必要的个人数据或凭据。

## Phase 10：移动端适配、存档、测试、发布准备

目标：完成面向公开发布的稳定性、兼容性和交付检查。

建议范围：

- `localStorage` 存档、恢复、版本迁移和损坏恢复；
- 主流移动浏览器与屏幕适配；
- 性能、资源体积、加载和离线异常处理；
- 完整流程回归、内容校验与结局覆盖测试；
- 基础可访问性、隐私说明和必要合规检查；
- 发布环境、错误监控策略和版本记录（是否接入服务由届时单独决策）。

验收标准：

- 刷新后可可靠恢复有效进度；
- 旧版本存档有明确迁移或回退路径；
- 目标移动浏览器完整通关无阻断问题；
- 构建产物、部署说明和发布检查表齐全。
